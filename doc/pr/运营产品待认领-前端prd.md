# 运营产品待认领-前端 PRD

## 1. 需求背景

当前运营产品在“认领/交接”过程中缺少统一的前端操作入口与审批界面，导致：

- 运营人员无法在产品分配页面快速发起待认领申请。
- 同一父体下子体存在多个负责人时，前端缺少明确提示和确认机制。
- 审批人无法集中查看待认领数据并执行审批。
- 用户无法从界面上判断当前记录是否已提交、审批状态如何。

因此，需要基于后端“运营产品待认领”能力，补充对应的前端交互方案。

## 2. 建设目标

- 在产品分配页面提供“标记待认领”操作入口。
- 在多负责人场景下，提供清晰的二次确认弹窗。
- 提供“待老品认领列表”页面，支持查询、筛选、分页。
- 提供审批操作入口，支持审批通过、不通过。
- 界面完整展示认领状态、提交人、原负责人、提交时间等关键信息。

## 3. 适用范围

本次前端需求包含：

- 产品分配页面新增“标记待认领”交互。
- 待老品认领列表页。
- 待老品认领审批交互。
- 与后端 3 个接口的联调处理。

本次不包含：

- 新的前端权限体系设计。
- 站内信、消息通知、审批消息提醒。
- 独立移动端页面。

## 4. 用户角色

- 运营人员：在产品分配页发起待认领申请。
- 审批人员：在待认领列表页查看并审批申请。

## 5. 页面范围

### 5.1 产品分配页面

在现有产品分配页面中新增“标记待认领”按钮。

使用场景：

- 用户勾选一条或多条产品分配记录后，点击“标记待认领”。

前端处理要求：

- 未勾选数据时，按钮可置灰，或点击后提示“请选择需要标记的数据”。
- 点击后调用后端标记接口 `/api/v1/mark/unclaimed`。
- 若后端返回成功，则提示“提交成功”，并刷新当前列表。
- 若后端返回多负责人冲突提示，则弹出确认框，由用户确认是否继续提交。

### 5.2 待老品认领列表页面

需新增独立列表页或在现有运营模块中新增菜单入口，用于展示待认领数据。

页面需包含：

- 关键词搜索框
- 审批状态筛选
- 查询按钮
- 重置按钮
- 列表表格
- 分页器

### 5.3 审批操作区域

在待老品认领列表中，对“待审批”状态的数据提供审批按钮：

- 审批通过
- 审批不通过

已审批数据不展示审批按钮，或按钮置灰不可用。

## 6. 页面交互设计

### 6.1 标记待认领交互

入口位置建议：

- 位于产品分配列表上方的批量操作区。

交互流程：

1. 用户勾选产品分配记录。
2. 点击“标记待认领”。
3. 前端调用：

```json
POST /api/v1/mark/unclaimed
{
  "ids": [1, 2, 3],
  "confirmSubmit": false
}
```

4. 根据接口返回结果处理：
   - 成功：提示“标记成功”或“提交成功”，刷新列表。
   - 普通失败：提示后端返回错误信息。
   - 多负责人冲突：弹出二次确认框。

二次确认弹窗要求：

- 标题：`提交确认`
- 内容：展示后端返回的冲突提示文本
- 按钮：
  - `取消`
  - `确认提交`

用户点击“确认提交”后，再次调用接口：

```json
POST /api/v1/mark/unclaimed
{
  "ids": [1, 2, 3],
  "confirmSubmit": true
}
```

交互约束：

- 重复点击时需防抖或按钮 loading，避免重复提交。
- 请求处理中按钮不可重复点击。
- 批量提交后需刷新当前产品分配页数据。

### 6.2 待认领列表查询交互

查询接口：

```json
POST /api/v1/unclaimed/list
{
  "keyWord": "",
  "pageNo": 1,
  "pageSize": 20,
  "status": 0
}
```

筛选项说明：

- 关键词：支持输入 `asin`、`parentAsin`、`sku`
- 状态：
  - 全部
  - 待审批
  - 审批通过
  - 审批不通过

交互规则：

- 页面首次进入默认查询第一页数据。
- 点击“查询”时重置到第一页。
- 点击“重置”时清空关键词、状态，并重新加载第一页。
- 翻页时保留当前查询条件。

### 6.3 审批交互

审批按钮仅在 `status=0` 时展示。

审批通过交互：

1. 点击“通过”按钮。
2. 弹出确认框。
3. 用户确认后调用审批接口。

审批不通过交互：

1. 点击“不通过”按钮。
2. 弹出审批弹窗。
3. 用户可填写备注后提交。

请求示例：

```json
POST /api/v1/unclaimed/approval
{
  "id": 1,
  "status": 1,
  "remark": "审批通过"
}
```

```json
POST /api/v1/unclaimed/approval
{
  "id": 1,
  "status": 2,
  "remark": "信息不完整，驳回"
}
```

交互约束：

- 审批提交中按钮需置为 loading。
- 审批成功后提示“审批成功”，并刷新当前列表。
- 接口返回“已审批”时，提示后刷新列表。

## 7. 列表展示设计

列表字段建议如下：

| 字段 | 说明 |
|------|------|
| ASIN | 对应后端返回 `asin` |
| 父体 ASIN | 对应后端返回 `parentAsin` |
| 亚马逊链接 | 对应后端返回 `amazonUrl` |
| SKU 信息 | 展示 `skuList`，格式建议为多行 |
| 站点 | 展示 `siteName` |
| 原负责人 | 对应 `originUserName` |
| 提交人 | 对应 `submitUserName` |
| 提交时间 | 对应 `submitDate` |
| 审批状态 | 展示状态文案 |
| 操作 | 审批按钮或“-” |

状态展示文案：

- `0` -> `待审批`
- `1` -> `审批通过`
- `2` -> `审批不通过`

状态展示建议：

- 待审批：橙色/警示色
- 审批通过：绿色/成功色
- 审批不通过：灰色或红色

SKU 展示建议：

- 每个 SKU 单独一行。
- 展示格式：

```text
SKU1 / 产品描述1
SKU2 / 产品描述2
```

若 `productDesc` 为空，则仅展示 SKU。

## 8. 弹窗设计

### 8.1 多负责人确认弹窗

- 触发时机：标记待认领接口返回“多负责人冲突”提示时。
- 标题：`提交确认`
- 内容：直接展示后端提示信息。
- 按钮：
  - `取消`
  - `确认提交`

### 8.2 审批确认弹窗

审批通过：

- 标题：`审批确认`
- 内容：`确认审批通过该待认领申请吗？`

审批不通过：

- 标题：`审批不通过`
- 内容包含：
  - 备注输入框
  - 提交按钮
  - 取消按钮

备注规则建议：

- 非必填
- 最大长度 500 字，与后端字段长度保持一致

## 9. 接口联调说明

### 9.1 标记待认领接口

- URL：`/api/v1/mark/unclaimed`
- Method：`POST`
- 用途：发起待认领提交

前端关注点：

- 处理成功返回
- 处理普通错误提示
- 处理“多负责人场景”的二次确认
- 处理重复提交错误

### 9.2 待认领列表接口

- URL：`/api/v1/unclaimed/list`
- Method：`POST`
- 用途：列表查询

前端关注点：

- 分页参数和分页组件联动
- 状态筛选与关键词搜索联动
- `skuList` 的格式化展示

### 9.3 待认领审批接口

- URL：`/api/v1/unclaimed/approval`
- Method：`POST`
- 用途：审批通过/不通过

前端关注点：

- 仅在待审批状态展示审批入口
- 审批成功后刷新列表
- 处理“当前记录已审批，请勿重复操作”等错误提示

## 10. 异常与边界处理

- 未选择数据点击“标记待认领”：提示用户先选择数据。
- 接口超时或网络异常：统一提示“请求失败，请稍后重试”。
- 接口返回业务错误：优先展示后端原始业务提示。
- 页面无数据：展示空状态。
- 已审批数据被重复点击审批：以前端控制为主，后端校验兜底。
- 列表中 `skuList` 为空：展示 `-`。
- 链接为空时，亚马逊链接列展示 `-`，不渲染可点击链接。

## 11. 权限与可见性

- “标记待认领”按钮需跟随产品分配页现有操作权限控制。
- “待老品认领列表”页面需纳入现有菜单权限体系。
- 审批按钮需按审批权限控制显示。

具体权限码或按钮权限标识以现有前端权限体系配置方式为准。

## 13. 验收标准

- 产品分配页面已新增“标记待认领”入口，并能正确提交选中数据。
- 多负责人场景下可弹出确认框，并在确认后继续提交。
- 已新增待老品认领列表页面，支持关键词、状态筛选、分页。
- 列表可正确展示 ASIN、父体、SKU、站点、提交人、原负责人、状态等信息。
- 待审批数据可执行“通过/不通过”操作。
- 审批成功后页面状态及时刷新。
- 各类异常提示清晰，不出现重复提交、重复审批的错误交互。
- 不修改后端 PRD 文档，仅新增前端 PRD 文档。
